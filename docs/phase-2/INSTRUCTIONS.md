# Phase 2 — First usable APK runner instructions

Read `docs/IMPLEMENTATION_PLAN.md`, Phase 0/1 results, and the current services/adapters before editing. Implement Phase 2 only. Keep the design small and preserve the existing architecture and Corvus themes.

1. Replace the developer APK-path workflow with one clear **Open APK** action and Explorer drag-and-drop. Picker and drop must call the same importer. Accept exactly one standalone `.apk`; explain rejected multiple files, AAB/APKS/XAPK, split sets and separate OBB inputs.
2. Inspect the APK using official tooling before installation. Read application/package identity, app name where available, version, minimum SDK, native ABIs and SHA-256. Compare with the selected device's reported SDK/ABIs. Do not blanket-reject ARM when the exact device reports support; actual translation still requires testing.
3. Persist one selected APK's source path, checksum, package/version identity, device identity and last successful installation metadata in the versioned settings model. Migrate existing Phase 1 settings non-destructively. Update successful-install metadata only after success. Handle missing or changed source files clearly. Do not add a package library/database.
4. For an unchanged previously installed APK, confirm the expected package/version is still installed on the same device and launch it without reinstalling. If the package is absent or the source changed, validate and install/update as appropriate. Do not trust desktop metadata alone.
5. Install compatible updates with data preservation. Report signature conflicts, downgrades, split-package requirements, insufficient space and compatibility failures clearly. Never silently uninstall, clear application data, force a downgrade or recreate the AVD to resolve an error. A failed import/update must retain the previous successful selection and device data.
6. Allow replacement of the selected APK. Other packages' Android data stays in the same persistent device unless explicitly removed in a separately authorized action. The product manages one selected APK, not a browseable library.
7. Add a compact toolbar for launch/relaunch, rotate, Back, Home, volume and fullscreen. Keep Google Play available from Android Home. Use the persistent input adapter for interactive controls and the session service for package/runtime operations; do not put SDK commands in views or spawn adb processes for gesture samples. Relaunch may restart the app but must preserve its data.
8. Show the selected app name/identity, meaningful device state and real preparing/starting/connecting/installing/ready progress. Keep operations asynchronous/cancellable and prevent conflicts. Release held inputs on focus loss, rotation, cancellation and shutdown. Games may enforce orientation; display geometry must track actual Android output.
9. Continue using the stable app-owned AVD. Closing visibly performs graceful asynchronous shutdown, flushes settings and releases input. Offer forced termination only after a failed/timed-out graceful shutdown. Never terminate unrelated devices or a shared ADB server.
10. Verify normal game saves through Android application data: install, play/save, close/reopen and cold boot. Verify compatible update retention, rejected-update retention and replacing selected packages. Desktop settings must not fabricate or write Android game saves. Do not implement snapshot/backup UI.
11. Add meaningful tests for shared importer validation, unchanged-installed launch, absent-package reinstall, changed APK update, selection/metadata commit on success only, settings migration, install failure/data preservation and conflicting-command protection. Run Windows integration checks with the diagnostic APK and one representative game. If a hardware check cannot run, give exact local steps and label it unverified.
12. Record runtime/image versions, transport status and actual results. Do not treat shell tests as proof of gameplay, audio, DPI input, saved progress or latency. If the provisional transport cannot meet core interaction/media requirements, document the failed requirement and resolve that integration before claiming Phase 2 acceptance.

Exit criteria: Open/drop/import and installed-app launch work; a compatible update retains real game progress; incompatible updates don't delete data; device controls and orientation are usable; closing/reopening preserves the same AVD and settings; errors are actionable and no implicit data deletion occurs.

Exclude Phase 3 installer/fresh-PC release work, soak/cycle certification, libraries/multiple devices, checkpoints/backups, persistent recording/replay editors/loops, instrumentation and iOS. Retain the existing Phase 0 diagnostic tools without turning them into Phase 4 automation.
