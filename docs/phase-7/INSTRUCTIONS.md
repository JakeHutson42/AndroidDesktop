# Phase 7 — consistent device backups and safe restoration

Source implementation is complete; real Android acceptance remains open. See [actual results](RESULTS.md) and [recovery runbook](RUNBOOK.md). The steps below record the authorized scope.

1. Read the canonical plan and Phase 0–6 results, profile/session/storage/ownership services and recovery rules. Resolve or explicitly retain outstanding hardware gates; establish actual device shutdown behavior before certifying consistent backups.
2. Scope explicit backup, verification and restoration for one selected profile. Keep one active device; defer live checkpoints, cloning, concurrency, instrumentation, remote access and iOS.
3. Require completed graceful shutdown, no surviving owned emulator/gateway/descendant process and an exclusive ownership lease before reading virtual disks. A force-stop or unknown shutdown state must not be presented as an application-consistent backup. Never copy running virtual disks as a consistent backup.
4. Stream files into a new staged destination with cancellation, free-space checks and bounded progress. Reject path traversal, junctions/symlinks and overlapping source/destination. Retain originals and previous completed backups. Handle SDK/shared-image dependencies explicitly rather than silently bundling them.
5. Record a versioned manifest with profile/device identities, runtime/image/configuration versions, file inventory/sizes/checksums, creation/shutdown evidence and consistency limitations. Verify the complete staged backup before publishing it atomically. Distinguish copied, verified and consistent states.
6. Before restoration, validate the manifest, file hashes, target identity, runtime/image compatibility and available space. Reject corrupted/incomplete/incompatible input. Explain that Android/Google credentials and online server state have distinct privacy/recovery implications; snapshots do not restore online state.
7. Restore into separate staging storage; preserve the original device and its metadata. Use a recoverable transaction/journal for directory and profile-metadata changes. Define crash/cancellation/failed-commit rollback before adding UI. Never overwrite the only copy of user data.
8. Reuse existing themed UI/adapters and asynchronous conflict guards. Add meaningful tests for integrity, compatibility, overlap/traversal, low-space/write/cancellation failures, partial restore/crash recovery and identity/library retention. Measure bounded memory and copy/verification performance on representative disk sizes.
9. On disposable real AVDs, demonstrate shutdown, backup, verified restoration and saved-progress retention, including cold boot and desktop restart. Preserve the original device until restoration is accepted. Fake file fixtures cannot certify Android disk consistency.
10. Update plan, dependency inventory, recovery docs and applicable candidate artifacts. Report passed/failed/unverified results and give the next scoped handoff. Do not start another expansion in the same batch.
