# Phase 3 — Release readiness instructions

Read `docs/IMPLEMENTATION_PLAN.md`, all Phase 0–2 result files, and the existing services/adapters before editing. Implement Phase 3 only. Keep the single-device/single-selected-APK scope and Corvus interface. Do not infer hardware acceptance from compiled code or fake tests.

1. Resolve the remaining runtime gate first. Validate one representative standalone game and the diagnostic APK on Windows: compatibility, streamed synchronized audio, touch/holds/swipes/multitouch, rotation, fullscreen/focus/mixed DPI, offline local media and reconnect. Select/document the transport only after measured success. If WebRTC fails, document the failed requirement and evaluate the planned scrcpy/native alternative; do not disguise the failure or adopt an untested workaround.
2. Pin the tested stable emulator/system-image/protocol and sidecar combinations. Record API, ABI, Google Play variant/revision, acceleration, Java, WebView2, GPU/driver and reference hardware. Review updates explicitly and rerun compatibility checks; no automatic prerelease installation.
3. Harden session recovery and lifecycle: missing/failed tools, boot timeout, cancelled install, lost signalling/media/input, crashed owned processes and failed shutdown. Keep data and selection intact, release held input and offer actionable retry/reconnect/stop paths. Forced termination remains an explicit recovery option after graceful failure. Never kill unrelated devices/shared ADB or reset Android data.
4. Verify cold boot and invalid Quick Boot recovery retain device disks and progress. Upgrading the desktop app must retain the same AVD identity/root and migrate settings non-destructively. Add no snapshot, backup or checkpoint interface.
5. Add bounded opt-in diagnostics and a useful support export containing runtime/configuration versions, session stages, errors and process/media measurements. Redact session tokens, authentication, discovery credentials and unnecessary personal paths. Report settings/evidence failures; do not let logging/archival work block gameplay.
6. Measure Release builds against standalone emulator and the selected embedded transport on the same device/workload. Report frame-time percentiles/dropped frames, input-to-visible distributions, added latency, decode/buffering behavior, CPU/GPU and memory across the process group. Confirm or explicitly revise the plan's budgets based on evidence; average FPS alone is insufficient.
7. Run a two-hour gameplay/diagnostic soak and twenty start/stop cycles. Inspect memory after warm-up, orphan owned processes, growing connections, graceful saves and recovery. Existing bounded diagnostic capture may be measured; do not build Phase 4 recording features to satisfy a soak.
8. Prepare a self-contained Windows x64 publish with packaged viewport assets and a dependable private gateway/runtime sidecar, or an already proven replacement. Normal users must not need npm, a development webserver, repository paths or a developer virtual environment. Preserve local-only endpoint authorization and restricted WebView navigation. Adapt Corvus publishing patterns rather than adding a large framework.
9. Build the Inno Setup installer with final product/version identity, dependency discovery and clear missing-prerequisite setup. Guide official SDK/image/Java/WebView2 installation, required license acceptance, actual download/storage information, cancellation and reboot resume. Reuse suitable existing SDKs and keep app-owned device data separate. Follow redistribution/license requirements; do not silently bundle unapproved SDK images or accept licenses.
10. Validate installation on a clean Windows machine, existing SDK configuration, missing dependencies, unavailable acceleration, insufficient disk, interrupted setup and image/version mismatch. Verify upgrade preserves settings/selected APK/AVD/progress. Uninstall must not silently delete the user's Android data; any removal choice must be explicit.
11. Complete third-party notices and the package inventory for distributed Corvus-derived resources, NuGet packages, gateway/browser components and private runtimes. Audit generated packages for accidental tokens, development paths, caches and test fixtures.
12. Add Windows CI for locked restore, build, meaningful tests and package-content contracts. Keep hardware emulator/game validation separate on a suitable Windows machine; CI unit success cannot certify WPF media, WHPX, GPU or game performance.
13. Deliver installer/publish artifacts, exact clean-PC and hardware validation instructions, known limitations, recovery guidance and an updated results record. Mark each check passed/failed/unverified based on an actual run. Do not label the release ready while core runtime, saves, setup or performance acceptance is still open.

Exit criteria: a fresh-PC installation works; the chosen runtime/transport meets the recorded compatibility/media/input budgets; repeated cycles and the two-hour soak pass; recovery/upgrade retain data; packages contain required local assets/dependencies and notices; no owned orphan processes or accumulating connections remain.

Exclude Phase 4 persistent recording/replay editors, loops and variation testing; APK libraries/multiple devices; profiles/backups; memory instrumentation; remote access and iOS. Phase 3 may be prepared while hardware is unavailable, but its acceptance cannot be claimed complete without those tests.
