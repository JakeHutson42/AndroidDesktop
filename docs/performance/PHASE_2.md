# Phase 2: native viewport prototype

The opt-in WPF native viewport is implemented. It hosts the Qt display window belonging to this application's emulator process tree, verifies PID/start time, and rejects incompatible DPI-awareness contexts before reparenting. The controller display remains the default and fallback. Native hosting is a feasibility prototype, not yet the production renderer.

See [native viewport polish and the latest measured checks](NATIVE_VIEWPORT_POLISH.md) for embedded-only startup/shutdown, dark margins, rotation and centered loading progress.

## Try it

Stop Android, expand Setup's advanced options, select **Experimental native viewport**, save, then start the device. Alternatively launch the Release executable with `--native-display` for a session that does not save the transport choice or other settings. To return to controller display, stop Android, clear the native option, select controller, save and restart. Both modes use the same persistent device.

Native presentation starts the emulator without `-no-window`, attaches its owned display to one `HwndHost`, and never connects the PNG gateway or WebView. No device wipe, APK reinstall, guest-data migration or authorization bypass is involved. The host keeps the child hidden and parented during normal emulator shutdown, then releases its reference after exit. Recovery detachment restores hidden window styles and bounds; it never presents a floating window or attaches by title alone.

The child uses physical client pixels and aspect-preserving letterboxing. Identical resize requests are skipped. The viewport remains mounted across shell navigation. Keyboard tab entry associates the owned emulator and host input queues while attached, verifies Windows focus and releases the association on detach. The existing Back, Home and volume buttons use owned-device ADB commands. Rotation is supported through the emulator console and Android user-rotation command. Recording/replay and audio remain unavailable in native mode; their controls are disabled.

## Measurements

Raw same-workload reports: [native](native-phase-2.json), [standalone](standalone-phase-2.json), [controller](controller-phase-2.json). Reproduce with a Release build and `./scripts/Test-RenderPerformance.ps1`; close Android Desktop normally first. Summarize CPU with `./scripts/Summarize-RenderPerformance.ps1`.

Hardware: Ryzen 9800X3D, RTX 5080, 32 GB RAM. Android Emulator 37.2.12, Android 14 Google Play x86-64, existing 1080 × 1920 device, two requested guest CPU cores and 2048 MiB requested RAM (the emulator raises RAM to its image minimum). All modes use `-gpu auto` and cold boot. Android's SurfaceFlinger reports the **NVIDIA GeForce RTX 5080 OpenGL ES translator**, and emulator logs confirm **WHPX operational**. These verify backend selection, not GPU-engine utilization or zero-copy presentation.

Each run returns to Android Home, settles for 15 seconds, and samples process CPU once per second for 20 seconds. CPU is normalized to total machine capacity; same-name processes are summed per sample. Diagnostic input and resize tests happen after CPU sampling. Figures are short, instrumented post-boot trials; background Android activity and separate cold boots introduce variation. They do not establish sustained gameplay performance or isolate the cost of reparenting.

| Display mode | Emulator mean CPU | WPF mean CPU | All sampled processes mean CPU | WPF queue probe p95 |
| --- | ---: | ---: | ---: | ---: |
| Native inside WPF | 13.75% | 0.26% | 15.14% | 0.079 ms |
| Standalone native | 7.87% | 0.21% | 8.24% | 0.114 ms |
| Controller | 15.78% | 0.41% | 19.68% | 0.415 ms |

Controller additionally used 1.82% CPU in Python and 1.27% across its WebView processes; neither ran for the native display. Embedded native's total was about **23% lower than controller**, but about **84% higher than standalone** in these trials. That difference requires profiling and repeated longer runs before attributing it to embedding. The current native implementation has not passed the performance gate for becoming the default.

[Controller media evidence](controller-media-phase-2.json) measured 7.85 received decoded frames/sec and 12.24 MiB/sec over its final 20 seconds. Video callback intervals were 130 ms median and 145 ms p95 across the media run. Those are pipeline callbacks, not verified on-screen frame pacing.

The dispatcher probe runs from a background task into WPF's input-priority queue. It measures queue response at the sample points, not input-to-visible latency. No native presented-FPS counter or video-based latency measurement is implemented. Removing the controller's 15 fps limit does not prove 60 fps delivery.

## Verification and remaining gates

- Real native boot and attachment, matching physical child bounds at 850 × 600, 1180 × 800 and 1440 × 900, repeated three-page navigation, fullscreen, minimize/restore, compatible 96-DPI contexts and normal teardown are covered by the benchmark. Native focus is checked using `GetGUIThreadInfo`.
- The native diagnostic test sends a centre tap through scoped Win32 window messages and a generated Down-arrow pair through Windows input, then checks Android diagnostic logs. The key pair is submitted only when this app owns the foreground root and the owned Qt child has focus; no desktop pointer movement or ADB-injected diagnostic event is used. Its receipt flags and coordinates are in the separate [native input report](native-input-phase-2.json); the three CPU reports skip diagnostic input when that APK is absent. The input test optionally receives the repository diagnostic APK as a fifth `--render-test` argument, installs it only if absent, and removes only that temporary installation after checking input. The tap reached Android at approximately (538, 960), including release. With the original hardware configuration, Windows accepted the generated key pair but Android did not report receipt. The AVD has `hw.keyboard=no` and `hw.dPad=no`; the separate [hardware-enabled test](native-keyboard-enabled-phase-2.json) enabled keyboard/D-pad support and disabled the lid switch, then restored the original configuration hash. Android reported the key release but no matching press even with an 80 ms hold. Full keyboard forwarding therefore **fails this prototype acceptance gate**; hardware settings alone do not resolve it. Isolate Qt forwarding versus standalone behaviour and use a supported input adapter before promoting native mode. This remains synthetic input-route validation, not full physical mouse/touch acceptance.
- Existing Tap Titans 2 package version and install/update timestamps are recorded after each restart. The benchmark never opens the game, accepts its terms, resets it or changes its data. Private saved-game integrity has not been independently inspected.
- Native teardown keeps the window contained/hidden until graceful emulator shutdown releases owned process handles. Repeated cold boots retain the installed package. Settings writes are disabled for benchmark and temporary native sessions.
- The standard and composition shell smokes both pass navigation/layout checks, including 60 page changes without viewport unloading. Standard mode also passes the extended screenshot/text-scale fixtures. Composition mode fails that extended preview scenario with native access violation `0xC0000005`; excluding the viewport during capture did not resolve it, while the navigation-only probe passes. The precise capture/layout failure is not isolated. `Test-Theme.ps1` therefore renders fixtures only in standard mode and retains composition navigation checks; this is not evidence that its preview problem is fixed.
- The persistent tab presenter prevents viewport unloading on navigation. Hover triggers only alter brushes; they do not change layout, templates or selection. Nested selection events no longer trigger shell input cancellation. The reported visual hover flicker has not been conclusively reproduced or declared fixed.
- Composition-preview stability, full native keyboard press/release, physical 125/150/200% scaling, mixed-monitor movement, continuous user-driven resize, physical pointer mapping across the viewport, held-key focus loss, native audio, automation/replay, accessibility, native F11/Escape routing and sustained game frame pacing remain acceptance gates. The latest containment checks cover hidden boot and shutdown with no observed detached visibility events. Native airspace requires hiding the host while displaying the centered startup panel.

Keep native mode opt-in until those gates pass. Cross-process Qt embedding is not a supported emulator frame-sharing API. Microsoft documents [DPI-mode risks with SetParent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent) and [shared focus/key state when joining input queues](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-attachthreadinput); this is why DPI rejection and focus teardown are explicit. Reject it if hardening exposes persistent correctness or resize problems, and follow the Direct3D/accelerated-video fallback gate in [the performance plan](../PERFORMANCE_PLAN.md).

Release builds pass with zero warnings/errors. All **133 .NET tests** pass, including physical-pixel aspect-fit and transport-conflict checks.
